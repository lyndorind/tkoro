# Лабораторна робота №7 — відповіді на контрольні запитання

### 1. Що таке оркестрація контейнерів і які основні завдання вона вирішує?

Оркестрація контейнерів — це автоматизоване керування життєвим циклом контейнерних застосунків. Вона відповідає за розгортання, запуск і перезапуск контейнерів, взаємодію сервісів, масштабування, перевірку стану, розподіл ресурсів і оновлення без значного простою.

### 2. Чим Docker Swarm відрізняється від Kubernetes?

Docker Swarm є простішим вбудованим у Docker рішенням для кластеризації та розгортання стеків. Kubernetes забезпечує ширші можливості планування подів, автоматичного масштабування, мережевої взаємодії, керування конфігураціями та розширення через контролери. Натомість налаштування й підтримка Kubernetes зазвичай складніші.

### 3. З яких основних розділів верхнього рівня складається файл compose.yaml?

- `services` описує контейнери: образи, збирання, порти, змінні середовища, залежності та перевірки здоров'я.
- `volumes` визначає іменовані томи для збереження даних між перезапусками.
- `networks` визначає мережі й правила зв'язку між контейнерами.
- `secrets` описує передавання чутливих файлів у контейнери.
- `configs` може передавати конфігураційні файли; `name` задає назву проєкту.

### 4. Чим відрізняються depends_on без умови та з service_healthy? Для чого healthcheck?

Звичайний `depends_on` задає порядок запуску, але не гарантує готовність залежного сервісу приймати запити. `condition: service_healthy` змушує Compose дочекатися успішного `healthcheck`. Параметр `interval` задає частоту перевірок, `timeout` — допустиму тривалість однієї перевірки, `retries` — кількість невдач до статусу `unhealthy`, `start_period` — початковий пільговий період для запуску.

### 5. Чим secrets безпечніші за environment?

Секрети зазвичай надаються контейнеру як змонтовані файли, доступ до яких обмежено, тоді як змінні `environment` можна випадково показати в логах, діагностиці або результаті `docker inspect`. Це зменшує ризик ненавмисного розкриття паролів. Водночас Compose secrets самі собою не гарантують шифрування локального файлу: файл-джерело та права доступу на хості потрібно захищати окремо.

### 6. Що таке інтеграційне тестування та чим воно відрізняється від unit-тестів?

Unit-тест перевіряє невеликий модуль або функцію ізольовано, наприклад валідацію `NoteIn`. Інтеграційний тест перевіряє взаємодію кількох компонентів: HTTP-запиту, FastAPI, драйвера `psycopg` і реальної PostgreSQL. Він виявляє помилки мережі, конфігурації, підключення до БД, SQL-запитів та форматів відповіді, які неможливо повністю виявити ізольованим тестом.

### 7. Які структурні елементи є у Postman?

Основні елементи — **collection** (колекція тестів), **folder** (група запитів), **request** (HTTP-метод, URL, заголовки, тіло), **variables** (адреси та дані між запитами), **environment** (набір значень для різних середовищ) і **scripts/tests** з перевірками `pm.test` та `pm.expect`. У нашій колекції `noteId` передається з POST у наступний GET.

### 8. Як виконувати інтеграційне тестування в GitHub Actions за допомогою services? Чим це відрізняється від Compose?

У job GitHub Actions блок `services` запускає залежну PostgreSQL в окремому контейнері з тестовими змінними та healthcheck. Runner запускає FastAPI, після чого Newman надсилає HTTP-запити й експортує HTML-звіт як artifact. Job із Postman може виконуватися паралельно з unit-тестами, якщо немає `needs`. `services` інтегрований безпосередньо в життєвий цикл GitHub Actions job; Docker Compose окремо описує багатоконтейнерний стек і зручний як для локальної розробки, так і для розгортання на ВМ.

### 9. Для чого навантажувальне тестування? k6, Gatling, Locust і JMeter — різниця?

Мета — перевірити затримки, пропускну здатність, стабільність і споживання ресурсів сервісу під одночасними запитами. **k6** використовує JavaScript-сценарії, **Gatling** орієнтований на кодові сценарії в Java/Scala/Kotlin, **Locust** описує поведінку користувачів через Python, а **Apache JMeter** має графічний редактор планів і XML-файли `.jmx` для автоматизованого консольного запуску. Вибір залежить від мови сценаріїв, вимог до звітності та середовища CI.

### 10. З чого складається план JMeter і чому запуск у CLI?

Типовий план містить **Test Plan**, **Thread Group** (кількість паралельних користувачів і повторень), **Samplers** (HTTP Request), **Config Elements** (спільні параметри), **Assertions** (перевірки результатів), **Timers** і **Listeners** (збір результатів). Консольний режим `jmeter -n -t ... -l ... -e -o ...` використовує менше ресурсів на графічний інтерфейс, тому краще підходить для навантаження та автоматичного запуску в CI. Зібрані дані можна оформити в HTML Dashboard.
